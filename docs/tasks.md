GMD-023 diagnosis and planned fix (2026-11-06):

- User logs: YOLO11 small initializes on WebGPU; RASHID-NEW at zoom 18 produces 79 ships for 2026-10-29 and 203 for 2025-03-27, each at 2427 × 1403 px. Only 2016-04-20 fails, with `No Wayback tiles returned`. The model load succeeds and 282 detections from two completed clips remain in memory/exportable; no 2016 result exists.
- `pickZoom` caps the AOI bounding-box tile count by lowering zoom, independently of date. Each source tile is 256 × 256 px; the default limit is 1200 tiles per AOI/date clip, not an object count or 1024 px model-input limit. The logged clip dimensions need roughly 60–77 source tiles depending on grid alignment. The same-AOI/date-independent limit does not explain a failure limited to 2016 after two zoom-18 successes.
- Read-only checks against Esri's current config identify release 388 as 2016-04-20. At the repository sample's centre (55.2735, 25.271), zoom-18 tile metadata returns `data:[0]`; its image request returns HTTP 404 without a CORS header. Zoom 17/16 image requests return JPEG/HTTP 200, and zoom-18 controls for 2025/2026 also succeed. This is confirmed sample-location evidence, not proof of coverage across the user's unsupplied RASHID-NEW polygon. [Recorded provider responses](./gmd-023-measurements.json).
- Root cause in the current handling: `fetchTile` collapses HTTP/network/bitmap failures into null; `buildRaster` combines all-tile failure into one generic network/CORS message, and its failure path does not shrink the allocated canvas. The job-level catch stops remaining clips. `All changes` looks up the centre at at most zoom 17, while raster processing can request zoom 18; a listed/manual release therefore does not guarantee coverage at the processing zoom or across the polygon.
- Planned: validate coverage at the selected effective processing zoom before large allocation; represent available/unavailable/unknown distinctly. Include AOI, date, release, zoom and failure classification in logs. Release canvases/bitmaps and cancel/drain requests on terminal failures. Retain completed clips and report per-clip failures/partial outcomes clearly in Results/exports; never turn missing coverage into a zero-object observation. Preserve cancellation behavior and actual georeferencing. Any alternative date or lower-zoom retry must be an explicit user choice, with separate detection-quality validation.
- Acceptance/tests: synthetic no-coverage, partial coverage, valid image, absent-CORS 404, network/timeout and decode-error fixtures; centre versus polygon/zoom mismatch; failed middle clip followed by a successful clip; all failed; cancellation; resource release; partial status in exports. Verify live service at the exact RASHID-NEW bounds when supplied. No implementation/status advancement or accuracy claim is made by this diagnosis.
